# 小程序真机卡顿优化方案

更新日期：2026-09-30

## 全局交互优化实施记录（2026-09-30）

本轮把范围从底部导航扩展到页面内所有点击。代码侧已经完成，真机 p50 / p95 和录屏仍需在实体 iPhone、Android 上补齐：

- 资料使用稳定内存引用；足迹写入改为不可变快照和串行异步持久化，并提供同步快照供页面立即展示。多页面继续共享 60 秒缓存和进行中请求。
- 地图、时光、我的页面增加可见状态与请求序号；隐藏页面不再应用过时异步结果。重复切页数据未变时跳过内容更新。
- 主导航使用轻量 `GrowthOverview`，不再执行两两距离扫描；成长详情先渲染基本内容，再以每批约 8ms 分帧检查「远方」成就。
- 时光页按日期、月份建立索引；时间线首次打开才生成。选中日和单日时间线均每批最多展示 20 条，可继续加载。
- 足迹保存后直接使用写透缓存计算到访次数；标记重要只更新当前记录和票根，不再重新加载详情。月报先打开，再后台保存已读状态。
- 照片上传最多 2 个并发，保留成功项并只重试失败项；存在待上传项时禁止保存。
- 自定义导航失败时回滚选中态；筛选关闭计时器移出渲染数据；图标、小拾和足迹卡避免相同输入的重复初始化。
- 地图页移除主要浮层的 `backdrop-filter`，缩小阴影，主导航页面取消小拾持续漂浮动画。

调试时在开发者工具控制台执行 `wx.setStorageSync('sgj:perf-debug', true)` 并重新进入页面，可获得 `[perf:interaction]` 和 `[perf:update]` 日志。日志只包含操作名、字段数量与耗时，不包含位置、照片或用户内容；测量后执行 `wx.removeStorageSync('sgj:perf-debug')` 关闭。

实体设备验收固定同一份 0 / 100 / 1000 条数据，每个核心操作重复 20 次，分别记录首次进入和重复使用。目标为本地点击反馈 p95 ≤100ms、轻量操作稳定 p95 ≤200ms、缓存命中时页面可交互 p95 ≤500ms，并较旧版本改善至少 40%。

## 实施记录（2026-09-30）

以下改动已落地并通过 `npm run check`（结构校验 + tsc + 81 个 vitest 用例），**尚未做真机 A/B 测量**，效果待基线采集后对比：

**P0 地图页（`miniprogram/pages/map/index.ts` 重构）**
- 完整足迹、ID 索引、过滤结果、缩放档位、标记索引全部移到页面实例；`data` 只保留 WXML 实际渲染的字段（移除了 `footprints`、`filteredFootprints`、`zoom`、`markerIdMap`、`clusterMarkers`）。
- 一次数据刷新合并为 1 次 `setData`（标记与视野仅在变化时追加，普通刷新最多 2 次）；新增 `applyFootprints` / `applyMode` / `applyFilter` 三个合并提交入口。
- 标记构建带缓存：数据版本 + 模式 + 聚合开关 + 缩放档位 + 标记/主题设置构成缓存键，命中即跳过 `markers` 提交。
- 热切回地图且数据引用未变时，`applyFootprints` 直接返回：不请求、不重算、不 setData。
- `fitToFootprints` 仅在首次加载、模式切换、筛选操作（用户主动改变可见集合）时调用；tab 返回与后台刷新保持视野。重复视野自动跳过。
- `regionchange:end` 以缩放档位去重：档位未跨越时不写 `scale`（消除写回循环与原生重绘）、不重建标记。
- 标记重建从"先建后移视野"改为"先定视野再建标记"，消除模式切换后标记停留在旧缩放档位的问题。

**P1 数据加载（`miniprogram/services/repository.ts`、时光页、我的页）**
- `listFootprints({ maxAgeMs })`：内存级共享缓存 + 进行中请求合并（in-flight Promise），地图/时光/我的热切页 60 秒内复用同一次云请求；写入/删除/清空经 `syncFootprintCache` 写透失效；`getFootprint` 优先读内存缓存。
- 时光页：按日分组预计算在实例上，选日 O(1) 查表；翻月/跳今天/跨月选中只重算当前视图字段（不再全量重算时间线与统计）；时间线分组按每页 10 组追加（`onReachBottom`），首屏节点数与总记录量解耦；完整列表移出 `data`。
- 我的页复用共享缓存，删除页内重复的 globalData 刷新逻辑。
- `computeGrowthSnapshot` 按（列表引用、档案、日）记忆化——地图/时光/我的/成长页共用一次计算，内部 O(n²) 最大距离不再逐页重复。

**P1 聚合算法（`miniprogram/utils/map.ts`）**
- `clusterFootprints` 从每点全量扫描（O(n²)）改为网格桶索引：仅查询所在桶及相邻 8 桶，保留原贪心合并语义（2~3 点不聚合、独立点补回、点击聚合放大）。实测 1000 点 ≈1ms，4000 点 ≈2.3ms（4 倍数据 2.5 倍耗时，近似线性）；新增同位置、稠稀混合不重不漏、跨经度边界 3 组测试。

**暂缓项（按本方案节奏）**
- 轻量摘要接口（P1 第 2 条）：日历预览与时光卡片需要 `photos[0]`，卡片需要 `note`，纯摘要会破坏现有展示；详情按需获取需要新增云函数 `get` 动作并核对 6 处消费路径。待基线测量确认网络占比后再推进。
- 云函数冷启动（P2）、地图 `backdrop-filter`/`filter` 的真机 A/B（需真机）、按视野裁剪标记数（需真机测量佐证）。

## 目标与当前结论

目标是让底部导航切换、地图拖动和缩放、冷启动在真机上保持可操作，并使足迹数量增加后性能仍可控。当前没有真机性能录制或耗时基线；以下热点来自代码检查，属于**待测量验证的假设**，不能视为已确定的卡顿原因。

之前已移除底部导航的模糊背景并减少地图首次进入时的一次重复刷新，但用户反馈真机仍明显卡顿。因此本轮重点是页面到渲染层的数据传输、原生地图标记更新、足迹全量加载及列表节点数。

## 先采集基线（P0，约半天）

在出现卡顿的手机上录制 10 次冷启动、10 次地图↔时光↔我的切换、连续拖动和缩放地图各 30 秒；再用一台中端 Android 和一台 iPhone 复测。固定同一份数据，分别覆盖 0、100、1000 条足迹；记录机型、系统与微信版本、网络、足迹数、地图标记数。冷启动和热切换分开统计 p50 / p95，不把网络等待混进纯渲染耗时。

| 指标 | 测量起止点 | 用途 |
| --- | --- | --- |
| 切页反馈与稳定耗时 | 点击 tab → 选中态变化；点击 tab → 目标页可交互且画面稳定 | 区分点击迟滞与页面渲染迟滞 |
| 页面生命周期耗时 | `onShow` 进入 → 首次内容 `setData` 回调；再结合真机录屏确认实际可见时间 | 定位 JS、数据桥或原生绘制 |
| 地图操作耗时 | `regionchange:end` → 标记更新完成及画面稳定 | 定位聚合计算与地图重绘 |
| 数据桥压力 | 每次操作的 `setData` 次数、字段、序列化后字节数、回调耗时 | 找出大对象和重复更新 |
| 网络与云函数 | `listFootprints` 请求耗时、返回条数/字节数；云函数冷/热调用分别记录 | 判断是否需要改接口及冷启动 |
| 流畅度与资源 | 真机性能录制中的长任务、掉帧、内存峰值、图片解码 | 找出原生地图或图片成本 |

测量代码仅在调试开关打开时记录，日志不要包含位置、照片、用户资料。先保存原始数据和录屏，再按下表的指标对比每阶段改动。`setData` 回调仅代表本次数据提交完成，最终视觉稳定时间仍以真机录制为准。

## 优先级与改动

### P0：减少地图重复计算和重绘（预计 1–2 天）

**代码依据：** [`map/index.ts`](../miniprogram/pages/map/index.ts) 的 `applyFootprints`、`updateModeView`、`renderMarkers`、`fitToFootprints` 在一次刷新中连续调用多个 `setData`，并把原始足迹和过滤后的足迹都放入页面 `data`。`fitToFootprints` 每次刷新都会重设地图中心和缩放级别。`onRegionChange` 在缩放结束时又可能触发标记重建。

1. 把完整足迹与 ID 索引保存在页面实例或共享缓存中；页面 `data` 只放 WXML 实际使用的字段。保留点击标记查找足迹的能力。
2. 一次数据刷新先在 JS 中算好当前模式、过滤结果、增长信息和标记，再合并提交必要字段；只有标记内容真正变化时才更新 `markers`。
3. 仅在首次定位、用户主动点“回到足迹范围”、或模式切换确需重定位时调用 `fitToFootprints`。普通 tab 返回和后台刷新保持用户当前视野。
4. 对 `regionchange:end` 的重复事件做去重；缩放没有跨越聚合档位时，不重建标记，也不反写相同的 `scale`。避免程序设定视野与 `regionchange` 相互触发。
5. 缓存由足迹版本、地图模式、过滤条件、聚合开关和缩放档位决定的标记结果。足迹变更时精确失效。

**验收：** 热切回地图且数据未变时，不重新请求足迹、不重算标记、不改变中心和缩放；普通刷新合并到最多 1–2 次必要的 `setData`。地图切换 p95 在同机同数据下较基线降低至少 40%，且无超过 1 秒的画面冻结。

### P1：让足迹数据按页面需求加载（预计 2–4 天）

**代码依据：** [`repository.ts`](../miniprogram/services/repository.ts) 的 `listFootprints` 请求完整列表；[`footprintMutation/index.js`](../cloudfunctions/footprintMutation/index.js) 的 `listOwned` 在服务端循环翻页后一次返回所有记录。地图、时光和我的页面都可能在缓存过期后使用这条路径。时光页 [`time/index.ts`](../miniprogram/pages/time/index.ts) 在日历模式下仍构建所有时间线分组，并把整个列表和回忆数据传给渲染层。

1. 统一足迹请求为共享的进行中 Promise，避免多个页面同时发起相同全量请求。切页先显示已缓存数据，后台更新完成后再局部刷新；写入/删除足迹时主动失效对应缓存。
2. 为地图和日历增加轻量摘要查询：只返回 ID、坐标、状态、日期及统计所需字段。详情在打开卡片时获取。按页返回结果并设置上限，避免云函数遍历所有页后再一次性传输。接口变更同时核对离线缓存、权限和数据一致性。
3. 时光页只计算和渲染当前视图：日历模式只加载当前月和选中日；时间线按页或按月追加，并对长列表使用分段渲染。图片使用缩略图及可见时加载。
4. 我的页复用共享摘要和已计算的统计结果，避免每次展示重复遍历全部足迹。

**验收：** 热切页无重复的同类云请求；首次传输量随当前视图所需数据增长，不随全部照片和足迹详情线性增长；1000 条数据的时间线首屏节点数保持有界，继续滚动仍能完整访问全部记录。

### P1：优化地图聚合与图层（预计 1–2 天）

**代码依据：** [`map.ts`](../miniprogram/utils/map.ts) 的 `clusterFootprints` 对每个点遍历全部点查找邻近项，最坏为 O(n²)。地图还会生成每个标记的配置和说明。地图样式中存在覆盖在地图上的模糊层以及地图滤镜，实际开销尚未测量。

1. 将聚合替换成网格桶或空间索引，让每点只查询所在桶及相邻桶；保留近邻合并、独立点、点击聚合放大的行为，并用稠密、稀疏、同位置及跨经度边界的数据验证结果。
2. 按当前视野和缩放级别限制一次提交给原生地图的标记数；低缩放优先聚合，高缩放再逐步展开。标记文字、图片和说明只在当前级别需要时生成。
3. 对地图上的 `backdrop-filter`、整图 `filter`、大量阴影及动画做逐项真机 A/B 对比。只有测出改善且视觉可接受时才移除或替换。

**验收：** 1000 条足迹时聚合计算随数据量近似线性增长；拖动、缩放时不存在持续超过 200 毫秒的卡住画面；所有原始足迹仍能通过聚合展开或列表进入。

### P2：仅在证据指向服务端时处理冷启动（预计半天至 1 天）

若真机数据表明主要时间花在云函数调用，区分网络、函数冷启动、数据库查询和返回体积，再决定是否优化函数依赖、初始化、索引或实例配置。CloudBase 官方建议先区分冷/热启动并查看日志，再针对初始化和依赖体积优化：[云函数冷启动优化](https://docs.cloudbase.net/recipes/optimize-cloud-function-wechat-miniprogram)。在没有调用分解数据前，不把增加云资源作为首选动作。

## 建议验收门槛与上线方式

这些是**建议目标，不是当前实测结果**；以最卡的真机为主设备，在采集基线后可调整：

- 热切 tab：点击反馈 p95 ≤ 100 毫秒，目标页可交互 p95 ≤ 500 毫秒；同时较基线改善至少 40%。
- 地图连续拖动/缩放：无超过 200 毫秒的明显冻结，标记稳定时间较基线改善至少 40%。
- 冷启动：先测出登录、请求、计算和地图绘制各段占比，再为“可操作首屏”设目标；不把未加载完的网络内容误判为不可操作。
- 正确性：地图模式、筛选、聚合点击、打卡、足迹新增/删除、离线缓存和时间线翻页均与当前行为一致。

每完成一阶段，在相同设备、相同网络和相同数据集下重复 10 次测量；保留前后 p50/p95、`setData` 次数/字节数、请求耗时与录屏。若 P0 后卡顿仍集中在原生地图绘制，再优先验证 P1 地图图层；若主要是网络，则先推进轻量摘要接口。每阶段单独提交并保留回退点，避免多个变量同时变化而无法判断收益。
